You are a senior Product Designer, UI/UX Architect, Frontend Prototyping Engineer, and Education Technology Product Specialist.

This is Phase 1 of a three-phase software development project.

**Phase 1 — Your responsibility:** Design and implement every important screen, component, navigation structure, workflow, interaction, and simulated operation required to demonstrate the complete product.

**Phase 2 — Another agent (Codex):** Will implement the complex desktop infrastructure, including Tauri, Rust, local database, peer-to-peer networking, encryption, licensing, desktop packaging, offline synchronization, security services, and desktop-to-browser connectivity.

Do not build a collection of static mockups. Build one coherent, navigable, interactive prototype with meaningful simulated application behavior.

### 3. CRITICAL ARCHITECTURAL CONCEPT — UNDERSTAND THIS FIRST

**There is no permanent admin computer, teacher computer, student computer, or central school server.**

Every installed desktop application is an independent peer.

Each computer:

1. Has its own local database.
2. Can function independently.
3. Can store its own and authorized replicated data.
4. Can discover and communicate with other installed computers.
5. Can initiate authorized synchronization.
6. Can receive data from other computers.
7. Can maintain pending transfers when another computer is unavailable.
8. Can participate in the examination process regardless of which user previously used it.
9. Can serve other computers while also requesting data from them.
10. Can retain data even after the sending computer disconnects.

**The currently authenticated user determines the application's available functions.**

Examples:

- An administrator logging into Computer A gets the administrator interface.
- A teacher logging into Computer A gets the teacher interface.
- A student logging into Computer A gets the student interface.
- Computer A does not permanently become an administrator, teacher, or student computer.
- Another computer can independently perform the same functions when an appropriately authorized user logs in.

The prototype must make this distinction obvious.

A school computer is a technical peer. A user is a person with permissions. An active session joins a user to a computer temporarily.

Do not design a master-server/slave-client architecture.

Any authorized peer may distribute approved examinations or collect results. A computer participating in an examination must not depend permanently on another computer to remain operational.

For the prototype, simulate each computer's independent local data and synchronization states.

Build the prototype as a runnable web application with real navigation and interactive UI.

- shadcn/ui or an equivalent accessible component library

Keep the frontend framework independent of Tauri-specific APIs so that the design can later be integrated into both the desktop application and the browser interface.

For Phase 1:

- No production database is required.
- No real backend is required.
- No actual peer-to-peer network communication is required.
- No real encryption or licensing implementation is required.
- No production authentication is required.
- No live AI service is required.
- No real desktop installer is required.

However, every corresponding feature must be represented by realistic screens, controls, workflows, state changes, success messages, error messages, and mock operations.

A button such as "Sync Assessment" must actually change the simulated peer state and produce an observable result. It must not merely display a decorative toast.

Never present simulated security or synchronization as if it were production-secure.

### 17. THE MOST IMPORTANT END-TO-END WORKFLOW

Implement this complete interactive scenario:

**Scenario: Teacher creates an exam, administrator approves it, distributes it to 100 computers, and later collects results.**

Step 1: A teacher logs into Computer 17.

Step 2: The teacher creates a Mathematics examination.

Step 3: The examination is saved locally on Computer 17.

Step 4: The teacher submits it for administrative approval.

Step 5: The teacher selects Computer 43 as the destination for the approval request, or sends the request to available authorized reviewers.

Step 6: An administrator logs into Computer 43.

Step 7: The administrator sees the pending assessment.

Step 8: The administrator reviews the assessment and approves it.

Step 9: The application records an approval associated with the correct version.

Step 10: The administrator opens the peer distribution interface.

Step 11: The administrator selects all 100 discovered school computers.

Step 12: The system starts simulated distribution.

Step 13: Each computer receives a separate local copy of the approved assessment.

Step 14: Show per-computer progress and acknowledgments.

Step 15: Simulate 96 successful transfers, three pending transfers, and one offline computer.

Step 16: Allow retry and reconnection.

Step 17: Students log into different computers and take the examination.

Step 18: Every student's answers are saved to their current computer's simulated local database.

Step 19: A computer disconnects during the examination.

Step 20: The student continues because the examination package has already been stored locally.

Step 21: Students complete their assessments.

Step 22: An administrator logs into Computer 8, which was not the original creating or approving computer.

Step 23: The administrator opens the result collection interface.

Step 24: The system discovers available peers and collects verified student submission records.

Step 25: Show 97 collected submissions out of 100 expected candidates.

Step 26: Show three outstanding results.

Step 27: Reconnect the outstanding peers or locate authorized replicas of their results.

Step 28: Complete collection of all 100 submissions.

Step 29: Display a consolidated result dashboard.

Step 30: Allow the administrator to export results and proceed with marking/moderation and publication.

**This scenario must be navigable and interactive from beginning to end.**

The prototype must show different local states on different simulated computers.

Switching from Computer 17 to Computer 43 must not automatically expose data that has not yet been synchronized or replicated.

### 38. FINAL INSTRUCTION

This platform's most distinctive feature is its autonomous, peer-to-peer, offline-first architecture.

Do not compromise that concept by designing the interface around a permanently designated admin computer, dedicated teacher computer, student computer, or mandatory central school server.

Any installed desktop computer can become an administrative, teaching, or student workstation depending on the authenticated user's permissions.

Each computer maintains independent local storage and participates in authorized data exchange.

Build the prototype to reflect this architecture consistently across all modules.

**The final prototype must be comprehensive enough that a separate engineer can understand the intended entire application by navigating it, and separate development agents can use its code, workflows, and documentation as the foundation for the production system.**
